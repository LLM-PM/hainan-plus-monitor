# 《海航PLUS权益票可购状态监控方案 v2.0》可行性评审

评审日期：2026-09-09　评审对象：方案 v2.0（2026-09-09）

---

## 0. 总体结论

需要把"方案是否可行"拆成两个独立问题，两者的答案完全不同：

| 问题 | 结论 | 评分 |
| --- | --- | --- |
| 作为**工程方案文档**是否合格？ | 合格，且明显高于同类个人工具的平均水平，可直接作为开发基线 | 8/10 |
| 作为**产品**是否值得投入？ | 可行性低。端到端成功（跑得起来 + 真的因此买到票）概率约 **20–30%** | 3/10 |

三个决定性风险，方案都没有充分定价：

1. **入口大概率已收进原生 App**（我判断 55–65%），一旦如此，第 04 章两条浏览器路径全部作废；
2. **30 分钟轮询对秒级消失的库存，捕获率可能 < 5%**——方案验证了"能不能查"，没验证"这个频率下能不能捕获"；
3. **账号风控代价未建模**——PLUS 卡是付费资产，封禁不可逆、无申诉。

**最重要的一条建议：在 P0 之前插入一个 P-1，只做两件不写代码的事**（成本几小时，决定后面 5–16 个开发日值不值得投）：

- 打开海南航空 App，人工确认 PLUS 专区是不是 H5、能否在独立浏览器直接打开——**30 分钟出结论**；
- 人工低频观测 3–5 天，记录目标航线机会的**出现频率与存活时长分布**，据此算期望捕获率。

现在的 P0 要 1–2 开发日 + 48–72 小时观察，却把最便宜、最能一票否决的判断放在了后面。

## 1. 方案做对的地方（这些应当保留）

这份文档的可靠性设计明显是有经验的人写的，以下几点是同类项目最常见的坑，方案都避开了：

1. **`queryStatus` 与 `availability` 分离建模**（第 05 章）。绝大多数爬虫项目把"请求失败"和"没有票"混为一谈，导致误报售罄。四值 `AVAILABLE/UNAVAILABLE/NOT_OFFERED/UNKNOWN` + "成功空列表只有在响应完整且语义明确时才算无票"，是整份文档最有价值的部分。
2. **观测 / 事件 / 通知三层分离 + outbox 模式**（第 07、08 章）。先落库再异步推送，避免崩溃后重复或丢失通知。
3. **`freshness` 由 `lastValidAt` 派生而非存储**，并明文禁止"扫描周期变慢时偷偷扩大 TTL 维持绿色状态"——这种自律在需求文档里很少见。
4. **`episode_id` 机会序号递增去重**。正确解决了"关闭后重开要再提醒"，比单纯用 `航班号+日期` 永久去重强。
5. **403/429 时禁止自动切路加压**（第 04 章故障表）。这是对平台的克制，也是避免风控升级的关键。
6. **`DELIVERY_UNKNOWN` 状态，不盲目重发**。对 PushPlus"同步受理 ≠ 最终送达"的理解准确。
7. **通篇 UNVERIFIED 标注 + P0 go/no-go 门禁**。方案没有假装数据源已经存在，这一点值得肯定。

## 2. 关键风险与缺口

### 2.1 【最高】入口迁移到原生 App 是最可能的结局，但概率未评估

方案自己引用的 [2][3] 已经说明：飞飞乐 App 关停，PLUS 权益迁移进海南航空 App。**这个迁移方向本身就是信号**——航司把权益兑换收进自有 App，通常伴随设备绑定与客户端签名的强化。

国内航司 App 的核心查询接口普遍带有：客户端计算的 `sign`/`token`、设备指纹、SSL pinning、第三方风控 SDK。若属实：

- 第 04 章的 Browser Network 与 Browser DOM **两条路径同时作废**；
- 只剩"设备端辅助方案"，即 Appium / 抓包重放 / hook——**成本与法律风险是另一个量级**，且大概率触碰"绕过技术措施"；
- 第 11 章的工期表整体失效。

方案在第 03 章表格第三行和第 11 章末尾都写了这个分支，处理是对的，**但没有给出概率判断**。我认为这是最可能的分支，应当前置到文档开头，而不是作为一个并列选项。

**建议**：明确写"若 P0 判定为原生 App 专用，本项目终止，另立项评估"，并把它标为**预期结果之一**而非例外分支。

### 2.2 【最高】没有验证"能不能捕获"，只验证了"能不能查"

方案第 01 章自己引了公告："199 元优惠客票数量动态变化，热门航线库存波动较大"。这类权益票的实际释放模式是**秒级放出、秒级被抢**，且盯着的人不止一个（包括用脚本的）。

粗略估算：若机会平均存活 `T`，轮询周期 30 分钟，则单次捕获概率 ≈ `T / 30min`。

| 机会存活时长（中位） | 30 分钟轮询的捕获率 |
| --- | --- |
| 30 秒 | ≈ 1.7% |
| 2 分钟 | ≈ 6.7% |
| 10 分钟 | ≈ 33% |
| 1 小时以上 | > 90%（此时也不太需要监控） |

方案第 10 章 A11 很诚实地写了"真实放票到发现的耗时不宣称可测"，但**没有把"预期捕获率"列为产品价值的核心指标**。这是决定项目值不值得做的唯一数字，却完全没有被估算。

还要叠加端到端延迟：用户收到通知时，平均已距离放票 **≥15 分钟**（轮询间隔的一半）+ 查询耗时 + 推送 + 用户反应 + 打开 App 下单。A11 只度量了"观测完成到推送提交 P95 ≤10 秒"，这一段在总延迟里占比极小，**度量了不重要的那一段**。

**建议**：P-1 阶段人工记录机会存活时长分布。若中位数 < 5 分钟，直接停止项目——工程做得再好也救不回来。

### 2.3 【高】账户风控代价完全未建模

整份文档把风险建模在"访问被拒 / 限流"上（A07、第 06 章退避规则），**没有任何一处评估"账户被风控 / 权益卡冻结 / 封号"的后果**。

对个人用户来说这是最实质的风险：

- PLUS 卡是**付费资产**，账号里还有里程与常旅客等级；
- 触发风控的代价不是"任务暂停"，是**资产损失，不可逆、无申诉渠道**；
- 第 06 章设定的**每天 700 次逻辑查询**，对单个个人账号是极高频次——正常用户一天查 5–20 次。700 次/天 ≈ 平均每 2 分钟一次，且要求连续 7–14 天（A10）。**这个行为模式在任何航司风控系统里都是显著离群点。**

**建议**：
1. 把"账户风控 / 封禁"列为独立风险维度，写入第 11 章"运行边界"，明确说明用户可能损失什么；
2. 预算下调一个量级（每天 50–100 次），并**接受覆盖率相应下降**；
3. 顺序要反过来——先定安全预算，再看能覆盖多少查询键，而不是用 A10 的 ≥90% 覆盖率去倒推预算。

### 2.4 【高】预算模型与覆盖率目标在数学上几乎不相容

把第 06、07、10 章的数字放在一起会发现内部矛盾：

- 14 个查询键 × 30 分钟一轮 = **672 次/天**，日预算 700，**余量仅 28 次**；
- 同时每小时 14 键 × 2 轮 = **28 次/小时**，小时限额 30，**余量仅 2 次**；
- 第 07 章的复查机制：每次发现机会后 60 秒复查一次。若一天出现 20 次机会，即 20 次额外查询，**直接吃掉日余量的 71%**；
- 加上重试、会话恢复验证、用户手工刷新、健康探测（方案明确要求全部计入预算）——**余量必然被击穿**；
- 而 A10 要求语义有效查询率 ≥95%、新鲜覆盖率 ≥90%，意味着系统必须**几乎不出错地跑满预算**才能达标。

另外，"每小时 30 次 × 24 = 720"与"每天 700"两个限额基本重合，说明小时限额**几乎不起平滑作用**——一旦某小时因故障堆积，立刻撞限。

**建议**：
1. 查询键数量砍到 **7–8 个**（1 条航线 × 7 天），或轮询间隔放宽到 45–60 分钟；
2. **MVP 直接关闭 60 秒复查**——对秒级消失的库存，60 秒后复查大概率返回 `NO_LONGER_AVAILABLE`（方案自己也说不能算误报），**几乎不产生信息量，只消耗预算**，把预算还给扫描；
3. 小时限额与日限额重新推算，留出至少 30% 的故障余量。

### 2.5 【中】会话寿命与"无人值守"目标冲突

航司 H5/App 登录态通常 7–30 天，但查权益、下单等敏感操作会触发重新验证或短信验证码。方案第 09 章明确"不处理验证码、MFA"，会话失效即暂停等人工——**边界设得对，但后果没算清**。

现实结果是**可能每隔几天就需要人工介入一次**。A10 要求 7–14 天连续运行且语义有效查询率 ≥95%，**一次会话失效持续 8 小时就会击穿这个指标**。方案第 263 行说"会话失效暂停计入缺口"是诚实的，但也等于承认 90% 的目标在现实下基本不可达。

**建议**：A10 改为"**报告实际值**"而非"达标 ≥95%/≥90%"。硬指标在不可控前提下只会逼着实现方作弊——方案自己已经预见到了这种作弊（偷偷放宽 TTL）并禁止了，那就不该再设这种指标。

### 2.6 【中】P0 的 go/no-go 门槛漏了"条款"这一票否决项

第 03 章"继续或停止"列了 5 条继续条件：正常可用入口、能区分权益与普通报价、结果一致、能识别失败、负载可运行。第 62 行提到"核对适用自动访问条款"，但**"条款是否允许自动化"没有被写进硬门槛**。

国内航司用户协议基本都含"不得使用任何自动程序、脚本、爬虫访问"之类的条款。**"条款禁止"与"技术上被拦"是两件事**——方案第 71 行只覆盖了后者（"必须绕过访问限制才能继续 → 不支持"）。严格按条款执行，P0 结论几乎必然是 no-go。

**建议**：把条款检查提为 **P0 第 0 步**，作为一票否决项，并明确写出"个人自用、不对外提供服务、低频"这一定性下的实际风险敞口。

### 2.7 【中】工期在其自身前提下仍偏乐观

P1 用 2–3 天完成 Adapter + 状态契约 + SQLite + 夹具，P2 用 2–3 天完成调度预算 + 去重 + outbox + PushPlus + 控制台 + 恢复。

单看代码量，熟练开发者确实能写完。但**反爬对抗的调试时间不可估**——选择器变化、异步加载时序、登录态刷新、页面 A/B 版本，这些在 Playwright 项目里通常占 **50–70% 的工时**。方案把"等待人工登录、第三方变更、观察期"单列了，但**没给对抗调试留 buffer**。

**建议**：P1/P2 各 ×2。基础开发 5–8 开发日 → **10–16 开发日**更现实。

### 2.8 【低】控制台技术选型过度

React + Vite 给 14 个查询键的个人工具做控制台是过度工程。一个服务端渲染的单页 HTML + 定时刷新完全够用，**能省 1–2 个开发日**。同理，`notification_outbox` 的 `lease_until` 在单进程并发 1 的前提下是过度设计（留着无害，但不必花时间做正确性测试）。

Node.js + TypeScript + SQLite + 单进程 + 并发 1 的主体选型是合理的，这个规模不需要 Postgres/Redis。

### 2.9 【建议补充】缺少 Plan B 的产品设计

方案第 03 章列出了"仅支持人工辅助"这个 P0 结论，但**没有为它设计对应产品**。考虑到 2.1 和 2.2 的判断，这其实是**最可能真正落地的形态**：

> 系统不自动查询，而是帮用户管理查询清单、按公开航线表 [4] 筛选候选航线与日期、记录每次人工查询结果、按设定节奏提醒用户自己去 App 查。

价值低于自动监控，但**完全合规、零账号风险、零维护对抗成本**，且现有的状态模型（第 05 章）和事件模型（第 07 章）可以原样复用，只是把 Adapter 换成人工录入。

**建议**：把这个形态明确设计出来作为 Plan B，并在 P-1 结束后就决定走 A 还是 B。

## 3. 修正后的建议路线

| 阶段 | 内容 | 成本 | 门禁 |
| --- | --- | --- | --- |
| **P-1（新增）** | ① 人工确认 PLUS 专区是否有独立浏览器可用入口；② 人工低频观测 3–5 天，记录机会出现频率与存活时长分布；③ 核对用户协议自动访问条款 | 几小时 + 3–5 天日历时间，不写代码 | 原生 App 专用 → **终止**；存活中位 <5 分钟 → **终止**；条款明确禁止 → **转 Plan B** |
| **P0** | 维持原方案，但预算下调至 50–100 次/天 | 1–2 开发日 + 48–72 小时观察 | 维持原 5 条 + 条款项 |
| **P1/P2** | 维持原方案，查询键砍至 7–8 个，关闭 60 秒复查，控制台改为最简 HTML | **4–6 开发日**（含对抗调试 buffer） | 维持 |
| **P3** | A10 改为报告实际值，不设硬性达标线；新增"实际捕获率"作为核心指标 | 7–14 天观察 | 捕获率是否支撑继续投入 |

## 4. 一句话总结

**这份文档的工程质量配得上一个严肃项目，但它严谨地论证了"怎么做"，跳过了"做出来有没有用"。** 在投入 5–16 个开发日之前，先用几小时回答两个问题：入口是不是纯原生 App，机会平均能活多久。这两个答案里任何一个不利，后面所有精心设计的状态机、outbox 和预算模型都不会产生价值。
