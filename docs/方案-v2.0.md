# 海航PLUS权益票可购状态监控方案

产品需求与技术实现方案

版本 2.0　编制日期 2026年9月9日　适用范围 个人单账户工具

## 01 项目定位与决策依据

本项目帮助已持有海航PLUS会员权益卡的用户，在有限航线和日期范围内持续查询可购状态，并在发现机会时提醒用户到官方渠道确认和购买。系统提供带时间戳的查询事实，不承诺锁票、出票成功、完整库存数量或捕获所有短暂机会。

建议先开展数据入口验证，验证通过后建设小规模MVP。现阶段可确定应用层设计，但不能承诺当前官方入口支持浏览器自动化、HTTP直接查询或长期无人值守。本文是开发基线，不是已实现系统或已完成实测的报告。

### 已核实的公开事实

- 海航2025年8月5日公告确认，199元优惠客票数量动态变化，热门航线库存波动较大；公告同时说明了当时最多保留3段未出行单程客票的限制。该历史规则不能代替用户当前所持产品规则。[1]
- CARNOC在澎湃平台发布的报道转述2026年1月8日公告：PLUS权益卡使用平台迁移至海南航空App，飞飞乐App将关停。海南航空App官方产品页更新记录包含PLUS权益兑换功能。本文据此以当前海南航空App内PLUS专区为入口核实对象，不假定旧飞飞乐接口仍有效。[2][3]
- 官方公开的参考航线表列明航线、航班和适用日期，并要求以实际查询为准；它可辅助筛选候选航线，不能用作实时权益库存来源。[4]

### 设计建议与待验证事项

设计建议：先验证一种查询渠道，采用单进程、SQLite和一个通知渠道；HTTP加速、多目的地和历史规律分析后置。

待验证：具体卡档位及规则版本、当前查询入口、浏览器独立访问能力、会话寿命、可读取字段、自动访问条款及限制、实际请求开销。未验证前，各项能力标记为UNVERIFIED，禁止在界面上显示为已支持。

本文中的请求预算、超时、成功率和工期均为建议初值或验收目标，不代表海航公布的访问许可、服务承诺或本项目已有实测结果。

## 02 用户需求与首版范围

核心使用流程：用户确认权益信息并完成官方登录，创建航线和日期任务；系统检查资格与请求预算后查询，保存观测结果，发现可购机会时推送；用户回到官方渠道确认并自行购买。系统对会话失效、查询中断和数据过期单独提示。

| 需求 | MVP实现 | 成功标准 |
| --- | --- | --- |
| 减少重复查询 | 单账户单程监控，任务可创建、编辑、暂停和删除 | 每个日期可查看最近尝试、最近有效结果和下一次计划 |
| 提醒新机会 | 首次发现可购、无票后恢复可购提醒 | 同一机会不反复提醒，再次开放可产生新事件 |
| 知道结果是否可信 | 显示当前查询状态、数据年龄、来源和原因 | 查询失败不能显示成售罄或继续显示为新鲜有票 |
| 知道监控是否运行 | 展示队列积压、请求预算、会话和通知状态 | 中断被识别，暂停原因清晰 |
| 人工接管 | 登录或验证由用户在官方入口完成 | 恢复后先验证一项查询，再渐进恢复任务 |

建议初始上限为1个账户、2条单程航线、每条不超过7个日期，共不超过14个查询键。允许增加任务草稿；超出容量时不自动开始查询，先展示预计扫描周期和预算影响。

每个任务必填：出发机场、到达机场、日期范围、权益档位及规则版本、权益有效期、期望扫描间隔、接收渠道。城市输入须解析为明确机场，跨机场组合由用户选择。查询身份以账户别名引用，不在任务内复制登录凭证。

### 后续范围

往返组合、多目的地组、HTTP加速、适用航线表辅助筛选和观测历史统计，在MVP验收后按实际收益选择。往返组合必须使用同一权益上下文下足够新鲜的双向结果，并检查到达时间、停留天数及账户限制；仅生成候选行程，不保证两段都能买到。

首版不含自动下单、占座、支付、取消订单、多人账户托管、跨航司独立接入和机器学习预测。运行任务不执行App安装、授权条款确认或验证码处理等人工步骤。

## 03 数据入口验证与继续条件

P0先产出证据再决定技术路径。验证仅查询，不提交订单；官方登录和身份验证由用户完成。使用目标账户实际适用的产品和航班样本，避免把普通现金票、积分奖励票或静态航线表识别为PLUS权益票。

| 入口实况 | 验证重点 | 决策 |
| --- | --- | --- |
| 浏览器可独立使用的H5 | 登录后能否查询；是否返回权益报价及可购标识 | 优先试验Browser Network |
| App内H5 | 是否依赖原生桥接、登录或设备上下文 | 只有独立浏览器正常可用时沿用此架构 |
| 原生App专用查询 | 浏览器不能复现完整正常查询 | 暂停本浏览器实现路线，另行评估设备端辅助方案 |
| 仅有公开航线表 | 有适用航线但无账户实时权益状态 | 只可做航线筛选，不能验收为监控系统 |

### 验证步骤

1. 记录实际App版本、专区入口、卡档位、规则来源及检查日期；查明是否存在正常可用的浏览器入口，核对适用自动访问条款。
2. 采集一组正常查询的脱敏证据，明确请求与响应的航线、日期、权益上下文和生成时刻。页面正常显示后，再判断网络响应或DOM是否可读。
3. 覆盖有权益报价、明确无权益报价、非适用日期、登录失效等场景；未能获得的真实样本标为未验证，不能用模拟样本替代业务事实验证。
4. 在目标运行设备低频观察48–72小时，记录每次查询结果、请求数量、会话续期、人工干预、访问限制及端到端延迟。出现挑战或明确拒绝时停止相关访问。

### 继续或停止

继续进入MVP须同时满足：存在正常可用入口；能区分PLUS权益与普通报价；结果与官方页面核对一致；能识别失败和会话问题；拟定负载可以运行，且访问边界清晰。

若只能读取航线表、无法证明报价属于当前权益、频繁要求人工验证，或必须绕过访问限制才能继续，P0结论为“不支持当前路线”或“仅支持人工辅助”。低频试验成功不能解释为长期访问许可或规模扩展保证。

P0交付物：入口说明、字段映射、脱敏样本、差异清单、能力矩阵、请求成本与运行记录，以及继续／调整／停止建议。证据中不保留Cookie、Token、身份信息或完整订单数据。

## 04 架构与查询渠道

采用Node.js与TypeScript单进程服务，包含REST API、Scheduler、Query Engine、状态计算和通知Worker；SQLite保存配置、观测与待发送事件。简单管理页可使用React与Vite。Playwright是否启用，由P0结果决定。

业务链路：任务配置 → 资格和预算检查 → 查询队列 → 已验证Adapter → 结果校验与标准化 → 数据库事务 → 通知Worker → 发送结果核对。

查询与通知之间以持久化事件隔离。服务先保存观测、状态变化和待发送记录，再异步推送；避免先推送后写库造成崩溃后重复或丢失。

### 按能力选择查询路径

- Browser Network：通过正常页面交互触发查询，被动读取响应。匹配请求参数、响应类型和业务状态；不得只因URL包含flight就采信结果。Playwright支持请求和响应事件监听。[5]
- Browser DOM：网络解析不可用且页面确实展示同一次完整结果时使用。校验当前机场、日期、权益标识、加载完成和结果新鲜度，不能解析上一日期残留页面。
- HTTP Fast Path：MVP不要求。后续仅在正常可访问接口和鉴权条件已验证时启用；优先评估browserContext.request共享Cookie的方式，其他Token和动态上下文仍须独立验证。[6]

每个浏览器Page同一时刻只服务一个查询键；首版并发为1。HTTP与Browser结果须通过同一份字段契约和语义测试，切换渠道不能凭空产生“新增库存”事件。

| 故障类别 | 行为 |
| --- | --- |
| HTTP路径自身不兼容 | 在预算内最多回退至已验证Browser路径一次 |
| 网络解析失败而当前DOM有效 | 读取DOM；记录降级与解析告警 |
| 登录失效或权益资格失效 | 暂停相关账户任务，等待用户处理 |
| 403原因不明或明确访问拒绝 | 暂停并诊断，不通过换路继续试探 |
| 429或限流信号 | 账户级退避；尊重Retry-After；禁止自动切路加压 |
| 上游故障或超时 | 有限重试后UNKNOWN，保留历史有效观测 |

三条路径共享上游和账户约束，不属于独立冗余系统。只有已验证的能力才可参与自动回退。

## 05 业务状态与统一数据契约

将查询是否成功、权益是否适用、报价是否可购及数据是否新鲜分开建模。AVAILABLE仅表示当前官方查询结果显示可购，不代表已锁定座位或最终出票成功。

| 维度 | 值 | 使用规则 |
| --- | --- | --- |
| queryStatus | SUCCESS／PARTIAL／FAILED | 部分响应不能证明未出现航班已经售罄 |
| eligibility | ELIGIBLE／INELIGIBLE／UNKNOWN | 记录产品、日期、账户额度等判定理由及证据来源 |
| availability | AVAILABLE／UNAVAILABLE／NOT_OFFERED／UNKNOWN | UNAVAILABLE须有明确有效查询证据；NOT_OFFERED须能确认未提供该权益 |
| freshness | FRESH／STALE | 根据lastValidAt和freshnessTtl派生，不覆盖原观测 |

成功空列表只有在响应完整且语义明确时才能表示“本次未返回可购权益报价”。未知空响应、页面未加载、错误页和字段缺失均为UNKNOWN，不能据此认定所有航班售罄。

### 必需字段

权益规则档案至少记录卡档位、有效期、适用航司及航班、排除日期、起飞时段、最晚购买时间、可保留未出行航段数和规则来源。仅按已确认规则筛选；无法获取账户剩余额度时标为UNKNOWN，提醒中说明资格待官方确认，不推断账户一定可购。

查询输入：queryId、accountRef、productProfileId、ruleVersion、originAirport、destinationAirport、departureDate、passengerCount。MVP固定1名成人；其他乘客组合不推断支持。

查询输出：queryId、queryStatus、contextVerified、resultComplete、requestedAt、observedAt、source、latencyMs、errorCode和offers。每个offer包含航司、航班号、出发和到达机场、当地完整起降日期时间、权益产品标识、eligibility、availability及reasonCode。

报价可选字段：amount、currency、taxAmount、totalAmount、quantityValue、quantityKind。quantityKind使用EXACT／LOWER_BOUND／UNKNOWN；来源不提供数量时quantityValue为空。没有明确税费信息时不得宣称报价为总价。最低价或普通现金价不能单独作为PLUS可购证据。

任务键：账户别名＋权益档位及规则版本＋机场对＋出发日期＋乘客组合。航班报价键在此基础上增加航司、航班号、航段和权益报价类别。多个Monitor共享相同查询键时合并查询，但保持各自通知订阅。

所有持久化时间使用UTC并保留业务时区Asia/Shanghai；用户按出发地日期查询，跨午夜到达使用完整日期时间。observedAt表示本系统观测时刻；上游更新时间只有明确返回时才记录，二者不能混用。

## 06 调度容量与请求预算

调度以“查询键”为单位，明确展示完整扫描所需时间。并发限制控制同时执行数量；请求预算控制总访问量，两者必须同时生效。

建议P0采用少量手工选定查询键。MVP初值为每个查询键30分钟一次、并发1、每账户每小时最多30次和每天最多700次远端逻辑查询尝试。回退、重试、主动刷新、二次确认及会访问上游的健康探测均计入预算。上述数值是项目内部上限，不是海航允许频率；若限制更严格或出现风险信号，立即降低或暂停。

一个逻辑查询可能触发多次HTTP请求。P0需测量实际查询相关请求量，同时统计页面附带流量；若无法计量，不得把逻辑预算当成真实网络负载。实际执行取逻辑预算、已核实上游限制和实测安全运行容量中的最严格边界。

### 容量示例

14个查询键、30分钟一轮，每天需要14×48＝672次正常查询，700次预算仅剩28次用于重试、确认和手工刷新。预算不足时顺延普通任务并展示实际周期，不隐藏跳过结果。若重试持续消耗余量，应缩小监控范围或延长间隔。

原先若扩展至5条航线×14天、每10分钟一轮，则每天为70×144＝10,080次逻辑查询。这个量级不能直接从个人少量查询验证推导可行。

### 执行规则

- 相同查询键只允许一个在途任务。下一次到期而上一次未完成时合并，不积累重复工作。
- 优先级为故障恢复验证、用户刷新、机会复查、普通扫描；所有优先级都受同一预算限制。为普通扫描保留调度份额，避免持续饥饿。
- 普通扫描加入小幅时间抖动以避免任务同时触发；不用于规避平台限制。过期日期、停用任务及确定不适用日期不查询。
- 暂定单路径超时30秒、单逻辑查询总截止60秒。仅网络瞬时故障允许最多一次重试；超时后取消旧任务，迟到结果不得覆盖较新观测。
- 暂定连续3次网络或上游错误进入15分钟冷却，再失败延长至60分钟。鉴权、拒绝访问和限流按专用规则处理，不等待错误次数阈值。
- 每日预算按Asia/Shanghai日期计；小时预算使用滚动窗口。服务重启后恢复已消费预算，避免清零形成突发访问。

默认freshnessTtl为45分钟，超时显示STALE。真实新鲜度按观测年龄计算；扫描周期变慢时不得偷偷扩大TTL维持绿色状态。历史驱动调度在样本充分前不启用。

## 07 事件与通知闭环

系统把“事实观测”“机会事件”和“通知发送”分开处理。事件必须包含查询上下文、首次观测时刻、事件编号、来源和当前可信程度。

| 情况 | 事件与通知 |
| --- | --- |
| 首次有效查询即AVAILABLE | FIRST_AVAILABLE，默认提醒一次 |
| 已确认UNAVAILABLE后出现AVAILABLE | OFFER_OPENED，生成新一轮机会并提醒 |
| AVAILABLE后再次AVAILABLE | 更新观测；默认不重复提醒 |
| AVAILABLE经短暂查询失败后恢复 | 更新状态，同一机会不重复提醒 |
| 观测中断超过TTL后再次AVAILABLE | 恢复提示可选；不能断言刚刚放票 |
| 有效结果显示不再可购 | OFFER_CLOSED，默认只记录 |
| 会话失效或持续中断 | 系统告警，恢复后发送一次恢复通知 |

### 去重与复查

事件去重键由报价键、事件类型和持久化机会序号组成；库存确认关闭后再次开放，机会序号递增。不能只用航班号和日期永久去重，否则会漏掉后续开放。重启和渠道切换不重置机会序号。

只有queryStatus为SUCCESS、上下文匹配、结果完整且权益可购标识明确的观测才生成机会提醒；资格未知时将提醒标为“发现权益报价，账户资格待确认”。初次观测证据充分时直接提醒。后台复查可配置为60秒后执行，但必须有预算；预算不足时标为NOT_RECHECKED并按正常扫描复查。复查结果分为CONFIRMED、NO_LONGER_AVAILABLE、RECHECK_FAILED；不能把后两项自动当作FALSE_POSITIVE。

通知内容示例：发现海航PLUS可购机会；航班及机场对；出发日期时间；报价及税费说明；观测于何时；复查状态；官方入口说明；“请在官方渠道确认，库存可能已变化”。仅使用已验证的官方深链接，否则提供文字操作路径，不拼接未知链接。

### 可靠发送

在同一SQLite事务内保存观测、事件和notification_outbox。Worker领取任务后提交PushPlus，记录供应商流水号，再通过发送结果查询或回调核对最终状态。PushPlus同步成功只代表请求被受理，不是最终推送成功。[7][8]

通知状态：PENDING、SENDING、ACCEPTED、SENT、FAILED、DELIVERY_UNKNOWN。请求超时但可能已被受理时先查结果；无法查证则保留DELIVERY_UNKNOWN，不盲目重发。已确认失败可按预算有限重试。外部渠道不能保证严格只发送一次，也不能把SENT解释为用户已读。

个人本机优先使用受支持的结果查询方式，避免为回调暴露公网服务。回调方案若启用，须验证来源、校验事件关联，并防止重复回调产生重复业务事件。

## 08 数据存储与服务接口

SQLite启用外键、WAL和合理busy_timeout，数据库保存在本地持久磁盘。统一串行提交短事务，不把浏览器等待或网络发送放进数据库事务。

| 表 | 主要数据和约束 |
| --- | --- |
| product_profiles | 档位、规则版本、有效期、人工确认的限制和来源；不存身份证信息 |
| monitors | 任务配置、订阅、启停原因、配置版本；编辑后重新校验容量 |
| query_runs | 查询键、尝试和完成时间、状态、错误类别、来源、预算消耗；保存失败记录 |
| offer_observations | query_run_id、报价键、业务状态、数量语义、价格、观测时刻；不可变历史 |
| offer_current | 最近观测、最近有效观测、机会序号；陈旧状态按时间派生 |
| inventory_events | 变化类型、前后观测引用、episode_id；事件键唯一 |
| notification_outbox | event_id、渠道、状态、重试次数、next_attempt_at、lease_until；订阅事件唯一 |
| notification_attempts | 供应商流水号、请求与结果状态、错误摘要；不存渠道密钥 |
| runtime_state | Adapter能力、会话状态、滚动预算、调度租约、最近成功时间 |

query_runs在请求前记录尝试并扣预算，实际观测完成后更新。服务启动时将遗留RUNNING任务标记为中断，按预算重新调度。事务完成前崩溃不会产生孤立待发通知；发送后崩溃通过供应商流水号尽量对账，无法确定时保留不确定状态。

### 本地API契约

| 接口 | 行为 |
| --- | --- |
| GET /api/capabilities | 返回入口验证、支持渠道与未验证能力 |
| GET／POST /api/monitors | 列出或创建任务；创建时校验日期、权益和容量 |
| PATCH /api/monitors/:id | 编辑或启停；使用配置版本防止覆盖旧配置 |
| POST /api/monitors/:id/refresh | 仅提交查询任务，返回202和runId；仍受预算限制 |
| GET /api/inventory | 返回状态、新鲜度、lastAttemptAt、lastValidAt和原因 |
| GET /api/events | 分页查询机会及系统事件 |
| GET /api/health | 查询、会话、数据库、通知、队列和预算健康度 |

不提供远程提交航司密码或绕过验证接口。所有配置写入须鉴权，刷新接口不可绕开访问控制或直接执行购买。

保留策略建议：详细观测7天、脱敏查询日志30天、变化事件90天；按需要保留更久的聚合。聚合记录查询次数、成功次数和观测机会数，不能将“发现次数”直接标成“真实放票概率”。原始响应仅在必要脱敏诊断中短期保存，默认关闭。

## 09 界面与运行安全

控制台以“监控是否正常”和“是否有新机会”为主，避免把Adapter细节放在用户主流程。查询来源和错误类别放入详情。

概览显示运行任务、可购机会、最旧有效观测年龄、暂停任务和通知异常。任务页显示机场对、日期、权益配置、期望／实际扫描周期和预算占用。库存页按日期列出航班、报价、观测时间和新鲜度；历史页展示机会及系统事件。系统页提供登录恢复提示、运行环境和诊断摘要。

AVAILABLE与STALE同时出现时，主文案为“历史查询有票，当前待确认”；UNKNOWN时明确显示“未获得有效结果”。每个页面都能看到最近成功查询时间，不能仅凭服务进程存活显示“监控正常”。

### 运行环境

首选个人长期在线设备，使用独立浏览器配置目录和专用运行账户。服务由进程管理器自动重启。浏览器崩溃后重建Context，并先验证查询再恢复任务；不得假定重启即可恢复登录。

Docker Compose作为可选部署方式，在目标环境重新验证浏览器、持久卷、字体和人工登录恢复流程后采用。本机验证结果不直接等价于服务器可用；服务器上的会话、网络出口和设备环境可能不同。

默认仅监听127.0.0.1。若确需远程管理，使用受控私网或HTTPS与强鉴权；校验Origin和跨站请求，限制访问范围。禁止将控制台、浏览器调试端口或会话目录直接暴露到公网。

### 凭证与故障恢复

- 浏览器Profile、storageState和渠道Token均视为敏感凭证，限制文件权限，不进入Git、截图、导出文件或普通日志。环境变量仅是注入方式，不等于加密存储。
- 不自动保存或填写用户航司密码，不处理验证码、MFA和条款确认。会话失效时暂停，用户在官方界面恢复后再验证。
- 数据库故障时停止新查询和事件发送，避免状态分裂；通知故障时继续预算允许的查询并积压outbox。
- 使用SQLite备份机制生成每日一致性备份；验证恢复一次。不要只复制正在写入的数据库主文件而遗漏WAL状态。
- 系统自行断网或整机离线时无法依靠自身发出告警。若要求离线通知，应单独配置外部存活监测，仅上报无个人信息的心跳；否则明确这一能力缺口。

核心指标包括语义有效查询率、最后有效观测时间、P95耗时、实际扫描周期、人工干预次数、限流／拒绝次数、过期数据比例及最终通知发送状态。HTTP 200不自动计入语义有效查询。

## 10 验收标准与测试矩阵

以下是建议验收目标，须在P0结束后结合实际访问约束确认。所有指标同时报告分母、观察时段和暂停时长；不能通过排除登录失效时段美化整体可用性。

| 编号 | 测试场景 | 通过标准 |
| --- | --- | --- |
| A01 | 权益结果核对 | 至少30组人工对照，覆盖有票、无票及不适用等可获得样本；无未解释语义差异；记录两次观察时间差 |
| A02 | 错误与部分响应 | 超时、空异常、缺字段、错日期、缓存残留、PARTIAL均不生成伪售罄或伪可购 |
| A03 | 首次及重复机会 | 首次可购提醒；连续有票不重复；确认关闭后重开再次提醒；重启不重置去重 |
| A04 | 陈旧与恢复 | 超过TTL按时显示STALE；失败不抹掉历史，也不继续宣称当前有票 |
| A05 | 复查 | 复查无票与复查失败分别记录，不能自动标为误报 |
| A06 | 预算与并发 | 刷新、回退、重试、重启均不突破预算；同一键无并行查询；预算不足可见 |
| A07 | 访问限制 | 401、403、429、验证码和明确拒绝触发对应暂停或退避，不换路加压 |
| A08 | 崩溃与事务 | 浏览器、Worker、服务重启及写库故障不会生成孤立事件；不确定发送状态可追踪 |
| A09 | 通知闭环 | 20次受控测试记录受理与最终发送结果，核对手机收到情况；失败或不确定均可解释 |
| A10 | 连续运行 | 7–14天记录；活动任务语义有效查询率目标≥95%，整体新鲜覆盖率目标≥90%；全部人工干预和中断列明 |
| A11 | 时效 | 无排队且渠道正常时，观测完成到推送提交P95≤10秒；最终发送耗时单列，真实放票到发现的耗时不宣称可测 |
| A12 | 运维与凭证 | 日志和导出不含凭证；外部不能访问本地管理API；备份恢复通过；离线监测能力明确 |

语义有效查询率＝满足上下文及完整性校验的成功查询次数／全部实际查询尝试次数。整体新鲜覆盖率＝用户启用监控期间，各查询键拥有新鲜有效观测的累计时长／应监控累计时长；系统故障及会话失效暂停计入缺口，用户主动停用不计入。

真实业务样本不足时，相应业务验收项保留“未验证”；测试夹具只验证解析、状态机与异常处理。少量抽样一致不能证明没有漏报，也不能证明实时库存准确率。

HTTP Fast Path、自动跨渠道降级、往返组合不作为MVP必须验收项。后续启用HTTP前，增加同上下文跨渠道结果对照、Cookie更新、拒绝访问处理与渠道切换不重复告警测试。

## 11 实施计划与交付边界

以下工期按一名熟悉Node.js与Playwright的开发者估计，前提是存在正常可用入口且不需要特殊设备改造。等待人工登录、第三方服务变更及观察期单列，不计为纯开发时间。

| 阶段 | 工作与交付物 | 建议投入 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| P0 入口验证 | 规则与入口、字段映射、脱敏证据、负载和会话记录 | 1–2个开发日，加48–72小时观察 | 数据语义和正常访问路径得到证明 |
| P1 查询闭环 | 一个Adapter、状态契约、SQLite、日志和夹具 | 2–3个开发日 | 正常与异常样本不混淆；结果可追踪 |
| P2 可用MVP | 调度预算、去重、outbox、PushPlus、简单控制台及恢复 | 2–3个开发日 | MVP功能和故障测试通过 |
| P3 运行验收 | 运行记录、人工对照、问题修复、备份恢复、操作说明 | 7–14天观察，另计修复投入 | 达到已确认目标或清楚说明未达标原因 |
| P4 可选优化 | HTTP加速、往返、多目的地、统计 | 按收益重新估算 | 已有MVP证据证明需要且可支持 |

基础开发估计5–8个开发日，另加观察与修复时间；不把所有能力压入3–5天承诺。若P0发现入口只能依赖原生App，停止沿用上述工期，先提交设备端方案及维护成本评估。

### 开发交付清单

- 源码与可复现启动说明，锁定依赖版本；配置模板只含占位值。
- 数据模型及迁移脚本、解析夹具、状态机和异常测试、备份恢复脚本。
- 入口与能力矩阵、字段证据、实际请求成本、稳定性和通知测试记录。
- 用户操作说明：创建任务、查看陈旧数据、暂停、恢复登录、处理通知失败和停止服务。
- 运行边界：已验证产品版本、支持入口和环境、未完成验收项、维护触发条件。

### 待确认记录

产品档位、规则版本、权益有效期、常用机场和日期范围、可接受提醒延迟、运行设备及通知渠道由项目使用者在P0确认。技术负责人记录查询渠道能力、访问限制与容量；未确认项不能默认成“无限制”或“支持”。

当规则或App版本发生影响性变化、解析差异出现、连续访问拒绝或人工维护成本过高时，暂停受影响能力并重新验证。仅在实际节省查询时间、提供有效机会且维护负担可接受时继续扩展。
